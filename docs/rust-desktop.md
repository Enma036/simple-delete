# Native Rust desktop version

Version 0.4 uses Rust 1.100, eframe/egui 0.37 and direct winreg access. It does not start Node, Electron, Chromium, a WebView or an HTTP server. The release executable links only Windows system DLLs. Windows PowerShell and reg.exe are used for Store packages, restore points and registry backup/import. No external scripts are needed beside the executable.

Build on Windows with `Build-Rust.ps1`. The current build uses the Rust GNU host and a portable MinGW-w64 compiler under `.codex/tools/rust-mingw/mingw64/bin`. The build script embeds the icon, sets static CRT linking, runs release tests and copies the executable to `dist/Simple-Delete-Rust.exe`. The executable is unsigned. The native UI requires an OpenGL-capable Windows graphics driver.

The native registry inventory is loaded on a worker thread and retained in memory. Search/sort recomputes only after inventory/filter changes; the app list renders only visible rows. Windows operations are performed on background workers, with results delivered over a channel and an explicit repaint. Destructive operations require a modal confirmation; candidate review and forced cleanup acknowledgment are separate.

Uninstall now retains the Windows process handle and waits on a worker for the vendor uninstaller to exit. Successful exit triggers an inventory refresh and leftover scan, then opens Cleanup automatically with every candidate unchecked. Cancellation and failure exit codes stop this sequence. If the application is still registered (for example, a launcher handed off to another process), Cleanup explicitly warns about it and does not enable forced removal automatically. No files are removed by the automatic scan.

The virtual list reserves exactly the height it reports for each row, truncates long text instead of changing row height, and uses a stable scroll identity. Other pages keep independent scroll positions. Wheel increments are reduced and scrolling requests continued animation frames. Regression tests cover long rows at narrow widths, uninstall/refresh/scan ordering, and cancellation preventing automatic cleanup.

The desktop interface uses a dark navigation rail, a cool light workspace, consistent cards, compact inventory summaries, and a prominent search field. App rows provide a primary Uninstall button; the adjacent menu contains Scan leftovers and Remove registration. Store, Startup, and Recovery reuse fixed-height virtual rows. Cleanup separates scanning, candidate review, and confirmation, with forced removal inside Advanced options. Page-specific empty states explain the next useful action. Original vector icons in `icons.rs` identify every category and navigation destination, with matching badges in app rows, suggestion cards, details and page headings. These represent categories, not individual application logos; they render locally at the current display scale without image downloads or an icon font.

Application identity tiles prefer actual local artwork: desktop `DisplayIcon` registry resources, an unambiguous executable in the install folder, or the Store package's manifest logo and qualified PNG assets. `app_icons.rs` discovers these on a worker; `icon_pixels.rs` decodes bounded PNGs or extracts 64px Windows icon resources without executing the file. GDI handles are released, alpha is reconstructed for legacy icons, and network/reparse paths are skipped. UI uploads are batched and textures/failed lookups are cached for the session. List scrolling performs no icon file access. Actual icons appear in the library, Store list, suggestions and details; unavailable artwork retains the category badge. Category and navigation icons remain custom vectors.

`catalog.rs` combines four registry branches (machine/user, 64/32-bit), live current-user Store packages, installed Steam manifests across declared libraries, and direct executable-containing folders in `%LOCALAPPDATA%/Programs`. Steam metadata fills missing size/location information for matching registrations. Discovery-only entries remain identifiable and cannot be passed to registry uninstall/removal actions. File size, path, reparse, count and time bounds limit metadata collection; failures and truncation appear under Detection notes. This is not an exhaustive scan of all drives or profiles. Source/scope are evidence labels; categories are local name/publisher heuristics.

`suggestions.rs` produces conditional review candidates from reported sizes of at least 2 GB and multiple distinct versions of the same normalized product/publisher. Identical duplicate registrations do not qualify as duplicate installations. Recognized dependencies, drivers, security tools and system packages are excluded, as are unverified folder-only entries. No usage-history inference, cloud service, automatic removal or claim of guaranteed reclaimable space is involved. Keep choices persist under `%LOCALAPPDATA%/SimpleDelete/kept-apps.json`. Details, review and confirmation remain separate steps.

Hydrogen implemented the backend, Terra supplied the initial egui interface, and another agent implemented native monitoring. Parent integration corrected cleanup selection to use candidate IDs, disabled implicit forced cleanup, added modal input blocking, cached filtering, virtualized rows, readable system fonts, manual orphan-name scans and operation-result refresh.

Monitoring captures uninstall identities plus directory metadata to depth 2, with 4,000 directory entries, a five-second enumeration budget and up to 4,000 registry identities retained. Reparse points are not traversed. Reports describe observed differences, preserve completeness warnings and explicitly do not claim causal installer attribution. Store/MSIX packages, file contents, drivers, services and tasks are not installation-traced. Sessions and backups persist outside the executable directory.

Validation: 40 optimized Rust tests pass, including fixture quarantine/restore, active/shared-location cleanup checks, registry target restrictions, uninstall parsing, startup backup/restore, Store removability checks, restore-point result validation, monitor diff/persistence and filtering. Diagnostics on this machine read 126 uninstall identities, 12 startup entries and 226 Store packages. The initial direct-registry read took 9 ms in one run; this is not a Revo benchmark or a general performance guarantee. The release executable's native window was opened and inspected. No real uninstall, startup disable, registry deletion, Store removal or restore-point creation was performed during validation.
